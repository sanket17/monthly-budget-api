## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Client -> GET /api/dashboard/ | Untrusted `?month=` query param, JWT-authenticated via the project-wide `IsAuthenticated` default. |
| dashboard/services.py -> transactions.services / credit_cards.services / budget.services | Internal composition boundary — every one of the five composed calls must receive `request.user.id` explicitly; there is no `UserScopedMixin` auto-scoping here since `DashboardView` is a plain `APIView`. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-06 | Elevation of Privilege (BOLA/IDOR) | dashboard/views.py::DashboardView | critical | mitigate | `DashboardView` is a plain `APIView`, not a `UserScopedMixin` `ModelViewSet` — scoping is entirely manual. `get()` derives `user_id` ONLY from `request.user.id`, never from `request.query_params` or the request body, mirroring `BalanceSummaryView`'s exact pattern. Every one of the five composed service calls inside `get_dashboard()` receives `user_id` as an explicit argument. A dedicated cross-user isolation test for the full response lands in Plan 05-05 (once all sections exist); this plan's own tests already prove each section individually only reflects the requesting user's data (each test creates exactly one user via `authenticated_client`/`user_factory`). |
| T-05-07 | Elevation of Privilege | transactions.services::get_emergency_fund_balance (category-name matching, consumed here) | low (confirmed not exploitable) | accept | Category-name matching could theoretically look like a cross-user vector, but every underlying query filters by `user_id` first (Plan 05-02's `_monthly_emergency_fund_totals`) — the name match only ever operates within one user's own category set, and D-03's "all matching active categories count" is scoped per-user by construction. Confirmed by Plan 05-02's cross-user isolation test. |
| T-05-08 | Information Disclosure / Denial of Service | dashboard/views.py::DashboardView (?month= param) | low | mitigate | `budget.utils.parse_month_param` already raises a DRF `ValidationError` on malformed input (existing control, reused verbatim here, not reimplemented). A dedicated malformed-`?month=` test for the dashboard endpoint is added in Plan 05-05 to confirm the existing control applies to this new call site too. |
</threat_model>
